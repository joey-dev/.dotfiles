# Claude workflow issues

These findings come from a static review of the workflow, its shipped configuration, and its tests. Runtime-dependent observations are marked below. See the [requirements inventory](WORKFLOW-REQUIREMENTS.md) for stage contracts and defaults.

## Stage execution and output

1. **Verify skips checks by default and runs configured commands on the host.** The shipped command list is empty, and a skip counts as success. When commands are configured, Verify invokes a shell or Nix directly and ignores the stage's restricted-network setting. It falls back to the original checkout without a recorded worktree. Host execution and the fallback need to be reconciled with the intended verification boundary. [Config](config.json) · [Verify](workflow/claude_workflow/stages/verify.py)
2. **Successful exits can advance the pipeline with missing or stale artifacts.** The headless helper trusts exit status and returns the expected path without checking it. Q&A and Retro do the same. Review can reuse old lens files or accept empty stdout. Implement can commit before the workflow notices a missing summary or plan. [Headless helper](workflow/claude_workflow/stages/base.py) · [Q&A](workflow/claude_workflow/stages/qa.py) · [Retro](workflow/claude_workflow/stages/retro.py) · [Review](workflow/claude_workflow/stages/review.py) · [Implement](workflow/claude_workflow/stages/implement.py)
3. **Plan can finish without an approved final draft.** The last rejected attempt triggers a revision and then returns success without reviewing that revision. Missing or malformed reviewer output can enter the revision path, and old output can survive reruns. The existing test explicitly expects success after reviewers exhaust the cap while requesting changes. Decide whether exhaustion should block or require human acceptance. [Plan](workflow/claude_workflow/stages/plan.py) · [Test](workflow/tests/test_pipeline.py)
4. **Code review is advisory even when it reports serious findings.** The pipeline checks reviewer process status and has no structured review verdict or return path to Implement. In automatic mode it moves straight to Retro. Review also falls back to diffing the current checkout against HEAD if implementation state is absent. [Review](workflow/claude_workflow/stages/review.py) · [Pipeline](workflow/claude_workflow/pipeline.py)
5. **Worktree reuse and commits can include unrelated changes.** Existing worktrees are reused based on the presence of `.git`, and an existing branch is checked out without confirming its relationship to the recorded base. Implement stages all dirty changes and commits before Verify or the human approval prompt. That matters when reusing a worktree containing manual edits or interrupted work. [Host helpers](workflow/claude_workflow/git_host.py) · [Implement](workflow/claude_workflow/stages/implement.py)
6. **Diff collection can fail on unusual untracked filenames.** The helper splits human-oriented filename output on newlines and passes each result as a filesystem path. Quoting in the listing can change the filename passed to the diff command. [Host helpers](workflow/claude_workflow/git_host.py)

## Resume, retries and checkpoints

7. **Approval gates are checkpointed as completed before the decision.** A stop at the prompt or an explicit abort leaves the stage complete. On restart the workflow can advance without approval. A retry runs the stage again but retains artifacts, sessions and existing worktree changes. [Pipeline](workflow/claude_workflow/pipeline.py)
8. **Explicit restarts retain downstream completion and skip prerequisite checks.** `--from-stage` starts at the requested stage even on a fresh ticket. Earlier-stage reruns leave downstream completion records intact. After a restart from a fully completed ticket, an interruption at a gate can leave the old downstream stages marked complete even though their inputs changed. [State](workflow/claude_workflow/state.py) · [Pipeline](workflow/claude_workflow/pipeline.py)
9. **Escalation can discard an unanswered blocker.** An exit code of zero clears the blocker without confirming answers were appended. The count is persisted before starting the session, so an interrupted or failed Q&A consumes an attempt. Escalations always start new sessions, and retrying a headless stage can process an old blocker again. The shared helper also recognizes blockers in Intake and Explore, beyond the Plan and Implement contract. [Pipeline](workflow/claude_workflow/pipeline.py) · [Headless helper](workflow/claude_workflow/stages/base.py) · [Shared skill](workflow/skills/shared/SKILL.md)
10. **Q&A and Retro reuse session IDs without checking that their sessions exist or are current.** An ID is persisted before the CLI starts. If launch fails before the session is created, the next attempt tries to resume that ID. A deliberate rerun also resumes the previous conversation. [Q&A](workflow/claude_workflow/stages/qa.py) · [Retro](workflow/claude_workflow/stages/retro.py)
11. **Concurrent invocations can collide.** The pipeline has no per-ticket lock. Runs for the same ticket share a fixed temporary checkpoint, the same artifact names, and a worktree. Atomic replacement protects individual completed writes but cannot coordinate multiple writers or make stage side effects transactional. Durability across power loss is also unverified because neither the checkpoint nor its containing directory is synced. [State](workflow/claude_workflow/state.py) · [Pipeline](workflow/claude_workflow/pipeline.py)
12. **Ticket IDs and persisted state lack validation.** The CLI accepts arbitrary ticket strings and the pipeline uses them directly to form paths. State and worktrees are keyed by ticket alone across repositories sharing the same configured directory. The loader accepts persisted ticket and worktree metadata without checking that they belong to the current invocation. [CLI](workflow/claude_workflow/cli.py) · [Pipeline](workflow/claude_workflow/pipeline.py) · [State](workflow/claude_workflow/state.py)

## Configuration and isolation

13. **Thinking is configured but unused, and tool enforcement needs integration evidence.** The launcher passes model and a conditional allowed-tools flag, but never reads the configured thinking level. The launcher requests permission bypass and does not pass an explicit tool list when the configuration is empty. The effective tool restrictions need checking with the packaged Claude version. [Runner](workflow/claude_workflow/claude_runner.py) · [Settings](../claude/settings.json)
14. **Intake relies on externally configured Atlassian MCP.** The shipped Intake MCP path is null. The sandbox may inherit a copy of the user's Claude configuration, but this role supplies no Atlassian server configuration and does no preflight check. A fresh installation has no guaranteed Jira connection. [Shipped settings](config.json) · [Sandbox](workflow/claude_workflow/sandbox.py) · [Intake](workflow/claude_workflow/stages/intake.py)
15. **The sandbox exposes more state than stage notes.** The writable notes mount covers the full ticket state directory, including checkpoints and the persisted Claude home. Every Claude stage shares that home. The host Claude settings and copied user configuration also affect runtime behavior beyond the mounted stage skill. Root repository metadata is masked, but there is no general guarantee that Git tooling is absent. [Sandbox](workflow/claude_workflow/sandbox.py) · [Shared skill](workflow/skills/shared/SKILL.md)
16. **Some sandbox and path settings are misleading.** The sandbox computes its working directory from repository availability and ignores the supplied working-directory field. Retro's configured read-only repository mode has no effect because Retro supplies no repository. The shipped JSON's explicit state and skills paths override the loader's XDG and skill environment defaults. [Sandbox](workflow/claude_workflow/sandbox.py) · [Retro](workflow/claude_workflow/stages/retro.py) · [Loader](workflow/claude_workflow/config.py) · [Shipped settings](config.json)
17. **Configuration errors may be accepted silently or fail late.** Some wrong types fall back to defaults, strings can be coerced into booleans or character-by-character tool lists, and review limits lack range checks. Missing optional paths can quietly disable a flake or MCP configuration. JSON, host helper, command launch, and prompt errors can also escape as exceptions instead of contextual stage failures. [Loader](workflow/claude_workflow/config.py) · [Sandbox](workflow/claude_workflow/sandbox.py) · [Pipeline](workflow/claude_workflow/pipeline.py)
18. **Proxy startup and connection cleanup are fragile.** The bridge starts in the background and immediately launches Claude without waiting for readiness. Client connections have no read deadline, and exiting the proxy context stops the listener without joining active handlers. The impact depends on client timing and connection behavior. [Sandbox](workflow/claude_workflow/sandbox.py) · [Proxy](workflow/claude_workflow/net_proxy.py)

## Packaging and coverage

19. **The shell launcher is empty.** `configuration/scripts/claude-workflow.sh` provides no entry point. The active role uses the packaged Python CLI. [Shell file](../scripts/claude-workflow.sh) · [Role](../../ai.nix)
20. **Tests leave the highest-impact integration paths unverified.** Pipeline tests largely use fake stages, the Plan cap test accepts exhaustion, and sandbox tests inspect command arguments. The suite has no live staged test covering Jira Intake, packaged Bubblewrap startup, interactive session recovery, artifact freshness, and verification through the installed CLI. The test command could not start in this review because `python3` was unavailable on PATH. [Tests](workflow/tests/)
